# Internationalization (i18n)

Pixel Lane is a trilingual product. This is a permanent, project-wide
requirement — see `AGENTS.md`'s "Internationalization — Mandatory" section
for the policy every agent must follow. This document is the workflow.

## Supported locales

| Locale | Language | Label      |
| ------ | -------- | ---------- |
| `kk`   | Kazakh   | Қазақша    |
| `ru`   | Russian  | Русский    |
| `en`   | English  | English    |

**Default locale: `kk`** (Pixel Lane is developed in and for Kazakhstan).
All three locales are first-class — none is a fallback or a partial
translation of another.

## Technology

[`next-intl`](https://next-intl.dev) v4, chosen because it has first-class
support for the Next.js App Router (Server Components, Client Components,
`generateMetadata`, static rendering via `setRequestLocale`) and was
already a good fit for this project's Next 16 / React 19 stack. There was
no existing i18n library in the project to extend.

## Routing

Locale-prefixed routes, always explicit (`localePrefix: "always"` in
`frontend/src/i18n/routing.ts`):

```
/kk                /ru                /en
/kk/features        /ru/features       /en/features
/kk/app/city-model  /ru/app/city-model /en/app/city-model
```

- `frontend/src/middleware.ts` runs next-intl's middleware for every route
  except `/health`, static assets, and Next internals — it resolves and
  persists the visitor's locale (via a cookie) and redirects unprefixed
  paths to their locale-prefixed equivalent.
- `frontend/next.config.ts` keeps the pre-i18n redirects from moving the
  internal app under `/app/*`, extended with locale-aware variants so an
  old bookmarked `/traffic` or `/kk/traffic` link still lands on
  `/kk/app/traffic` instead of 404ing.
- `/health` is a technical status page and is intentionally **not**
  localized — it lives outside the `[locale]` route segment with its own
  root layout (`frontend/src/app/health/layout.tsx`).

## Where translations live

```
frontend/messages/
  kk/
    common.json       marketing.json     auth.json
    dashboard.json     cityModel.json     traffic.json
    infrastructure.json simulation.json  analytics.json
    incidents.json      emergency.json    settings.json
  ru/  ...same files...
  en/  ...same files...
```

One JSON file per domain namespace, mirrored exactly across all three
locale directories. `frontend/src/i18n/request.ts` loads and merges them
per-request; the namespace list there is the single source of truth for
which files must exist.

**Do not** put the whole product's copy into one giant file, and **do
not** translate arbitrary domain/database data (city names, street names,
IDs, backend enum raw values) — only UI chrome and copy. `cityModel.json`'s
`severity.*` keys are the one exception worth noting: they map the
backend's congestion/severity enum to a human label, via
`frontend/src/features/city-viewer/lib/traffic-level.ts` and
`TrafficLevelBadge`, so a raw English enum value is never shown directly.

## Adding a translation key

1. Add the key to `frontend/messages/en/<namespace>.json` first.
2. Add the same key, translated, to `ru` and `kk` in the **same change**
   — never merge a feature with a key missing from any locale.
3. Read the key with `useTranslations("<namespace>")` (Server or Client
   Components — next-intl supports both directly) or, inside an `async`
   Server Component / `generateMetadata`, `getTranslations` from
   `next-intl/server`.
4. Run `npm run check:i18n` before committing.

## Adding a new localized page

1. Create the route under `frontend/src/app/[locale]/...` (inside the
   `(marketing)` group for the public site, or `app/` for the internal
   platform).
2. Add a namespace (or extend an existing one) for its copy.
3. Add `generateMetadata` using `getTranslations` for a localized
   `title`/`description` (and `alternates.languages` for public routes,
   so all three `hreflang` variants are discoverable).
4. Use `Link`/`redirect`/`usePathname`/`useRouter` from
   `frontend/src/i18n/navigation.ts` instead of `next/link` /
   `next/navigation` so links keep the current locale prefix. The one
   exception is the unlocalized `/health` route, which should be linked
   with plain `next/link`.

## Switching locale

`frontend/src/components/ui/LanguageSwitcher.tsx` is the single reusable
switcher (used in the marketing header/mobile nav and the app
header/sidebar). It calls `useRouter().replace({ pathname, params },
{ locale })` from `next-intl`'s navigation APIs, which swaps only the
locale segment and preserves the rest of the path — e.g. `/ru/features` →
`/en/features`, never a reset to the homepage. next-intl's middleware
persists the choice in a `NEXT_LOCALE` cookie automatically.

## Naming conventions

- Namespace files are `camelCase.json`, named after the feature/page they
  cover (`cityModel.json`, not `city_model.json` or a generic `misc.json`).
- Keys are `camelCase`, nested to mirror the UI structure (e.g.
  `marketing.hero.ctaExplore`).
- Where the same concept differs from a UI label to a semantic status,
  e.g. feature "status" fields, keep the value an untranslated **id**
  (`available` / `inDevelopment` / `planned`) and look up its label via
  `common.featureStatus.<id>` — never store the same status text twice
  per locale.

## Running the validation

```bash
cd frontend
npm run check:i18n
```

Fails if a namespace file is missing for a locale, or if the same
namespace has a different key set between `kk`, `ru`, and `en`. Part of
the normal pre-ship validation set alongside format/lint/typecheck/test/
build (see `AGENTS.md` § 17 and the `pre-ship` skill).

## Adding a fourth language later

By design, this does not require rewriting routing or component
architecture:

1. Add the locale to `frontend/src/i18n/routing.ts`'s `locales` array.
2. Add a `messages/<locale>/` directory with every namespace file.
3. Translate.

`generateStaticParams` in `frontend/src/app/[locale]/layout.tsx` and
`check:i18n` both derive from the same locale list, so nothing else needs
to change structurally.
