# AI Development Workflow — Pixel Lane

This document explains how AI agents (Claude Code, Codex, Gemini) operate in
this repository. The authoritative rules live in `AGENTS.md`; this document
explains the *workflow* around those rules in more detail. Avoid duplicating
rule text here — link back to `AGENTS.md` sections instead.

For a verified (not assumed) account of what each agent actually discovers,
what's confirmed vs. inferred, and where the setup is weak, see
`docs/ai-agent-audit.md`.

For how *humans* should write prompts for these agents (a reusable
template, required sections, examples, anti-patterns), see
`docs/ai-prompting.md`.

## Agent entry points

- **Claude Code** reads `CLAUDE.md` first (repo root and `frontend/`), which
  points to `AGENTS.md` and adds a Claude-specific commit-attribution rule.
- **Codex** reads `AGENTS.md` directly (its native convention) and uses
  `.agents/skills/`. AGENTS.md § 20 states explicitly that it is canonical
  for Codex.
- **Gemini** reads `GEMINI.md` first, a short entry point that points to
  `AGENTS.md` the same way `CLAUDE.md` does.
- All three follow the same policy — there is one shared source of truth
  (`AGENTS.md`). Agent-specific files are bootstraps/pointers, not separate
  policies.

## Agent instruction hierarchy

```
AGENTS.md                    canonical, cross-agent policy (all rules live here)
    ├─ CLAUDE.md              Claude Code entry point: points to AGENTS.md,
    │                         adds Claude-only commit-attribution rule
    │   └─ frontend/CLAUDE.md same pattern, scoped to frontend/, notes that
    │                         frontend/AGENTS.md is Next.js-generated (not
    │                         policy) so it doesn't get mistaken for one
    ├─ GEMINI.md               Gemini entry point: points to AGENTS.md,
    │                         restates the i18n requirement as reinforcement
    ├─ Codex                  no dedicated file; reads AGENTS.md natively
    └─ .agents/skills/*        task-specific checklists; assume AGENTS.md is
                              already known, never restate its rules
```

Notes:

- `frontend/AGENTS.md` is auto-generated by `next dev` on every dev-server
  start (framework/Next.js conventions only) — it is **not** a project
  policy file and must never be edited for policy content. Policy for the
  frontend lives in root `AGENTS.md`, referenced from `frontend/CLAUDE.md`.
- No nested `AGENTS.md`/`CLAUDE.md` exists under `backend/` or
  `simulation/` today — those subsystems are governed entirely by root
  `AGENTS.md`. If one is added later, keep it additive (domain-specific
  rules only) and never restate or contradict root policy.
- `node scripts/check-agents.mjs` (or `make check-agents`) is a lightweight
  filesystem/text check: it confirms the required instruction files exist
  and still cross-reference `AGENTS.md`. It cannot prove that any agent
  actually reads or obeys them at runtime — see the audit doc for that
  distinction.

## Startup protocol (required before implementing a non-trivial task)

Before writing any code, an agent must:

1. Read `AGENTS.md`.
2. Read its own agent-specific entry point if one exists (`CLAUDE.md`,
   `GEMINI.md`; Codex reads `AGENTS.md` natively — no separate file).
3. Read the relevant `.agents/skills/` checklist(s) for the task type.
4. **Resolve the task**, in this order:
   a. If the agent has working Notion MCP access, fetch the actual task
      (Task ID, Goal, Module, Scope, Acceptance Criteria, Dependencies)
      from the Development Workspace — see
      [docs/development/notion-mcp.md](development/notion-mcp.md). This is
      the preferred path when available, for any agent (Claude Code,
      Codex, Gemini CLI, or another compatible agent) — Notion MCP access
      is not Claude-specific.
   b. Otherwise, use the task content the human provided directly in the
      prompt (see [docs/ai-prompting.md](ai-prompting.md)'s Form B) or
      copied from [docs/development/task-template.md](development/task-template.md).
5. **Verify** the Task ID, scope, and acceptance criteria are actually
   present from step 4 — not inferred.
   **If task context cannot be resolved by either path — STOP before
   implementing anything and ask for the task content or the specific
   missing fields.** Never infer a goal, scope, acceptance criteria, or
   dependencies from a Task ID, a task title, or the product roadmap alone;
   a title like "PL-042" or "fix junction rendering" is not a substitute
   for the actual Goal/Scope/Acceptance Criteria fields.
6. Read only the relevant architecture/product docs for the area in scope
   — not the whole repository (AGENTS.md § 2, § 19).
7. Inspect the actual current implementation of that area.
8. If changing a shared/public boundary, inspect its callers/consumers
   first (AGENTS.md § 19).
9. Read the tests covering the affected behavior.
10. Compare the resolved task's assumptions against what steps 6–9 actually
    found.
11. Explicitly report any meaningful mismatch — a task description that
    assumes something is broken/missing/present when the repo shows
    otherwise — instead of silently working around it or silently trusting
    the description.
12. Only then implement, validate, and prepare the change for review.

An agent must never blindly trust: the user's own description of the
current state, an AI-generated plan, a stale prompt, Notion text that
contradicts the current implementation, or a previous agent's summary —
the actual repository and canonical docs are what's verified against.

## Task-scoped behavior

Treat the task (a Notion Task ID, or an explicit user request) as a
contract, per AGENTS.md § 17's completion checklist ("task scope matched
the actual change — no unrequested scope creep"). Concretely, do not:
redesign unrelated modules, rewrite working architecture, "clean up"
unrelated code, change unrelated UI, upgrade dependencies without need,
change the database schema unnecessarily, add speculative features,
implement a later roadmap item, or otherwise silently expand scope. If a
separate problem is discovered during the work, report it — don't solve it
unless it actually blocks the requested task or the user explicitly
approves the expanded scope.

## Context efficiency workflow

Before touching code:

1. State the task scope in one or two sentences (what modules/files are
   plausibly involved).
2. Search first (grep/glob/symbol search) to locate relevant files, routes,
   components, services, and tests.
3. Read only the files needed to make a correct, safe change.
4. If the change touches shared/core code, look at its consumers before
   editing.
5. If new evidence shows another module is affected, expand scope — do not
   silently ignore it to save tokens.

Full rules: see AGENTS.md § Context efficiency rules.

## Large codebase navigation workflow

As the repository grows, don't try to hold it all in context:

1. Identify the subsystem the task belongs to and read its public entry
   point first (e.g. `TrafficEngine.analyze(...)`, the city
   service/repository/schema, the viewer's feature entry component) before
   its internals.
2. Check for a subsystem-level `README.md`/`ARCHITECTURE.md` and read that
   before the code, if one exists.
3. Read `docs/architecture.md`'s subsystem map for where things live and
   how dependencies are supposed to flow.
4. Before changing a public contract, find its consumers/callers/tests/
   docs first.

Full rules and the source-of-truth hierarchy: see AGENTS.md § 19 (Large
codebase navigation).

## Security workflow

1. Determine whether the task is security-sensitive (touches auth, input
   handling, file access, external requests, secrets, permissions, etc.).
2. If yes, run the `security-review` skill (`.agents/skills/security-review`)
   before declaring the task complete.
3. Apply the hard rules in AGENTS.md § Security rules (no hardcoded secrets,
   no real secrets in `.env`, backend enforces authorization, no sensitive
   data in logs, no leaked stack traces).
4. Record findings and confirm they were addressed or explicitly accepted
   by the user before shipping.

## Testing workflow

1. Use the `testing` skill for guidance on what kind of test fits the change.
2. Add/update tests that validate real behavior, not tests written to pad
   coverage.
3. Run the smallest useful validation first (e.g. the touched module's unit
   tests), then broader validation (full suite, integration, build) if the
   change's scope warrants it.
4. Never claim a test or check passed without actually running it — if a
   command can't be executed in the current environment, say so explicitly.
5. Tests must reflect real architecture — do not validate PostgreSQL-
   dependent behavior against SQLite or another substitute (AGENTS.md § 8).

## Scalability and technology-selection workflow

1. Before introducing anything new (dependency, database, framework,
   infrastructure component), run the library-first evaluation in
   AGENTS.md § 18 — don't add it just because it's popular, and don't
   hand-write what a mature library already solves well.
2. Default to the project's production-grade technology (PostgreSQL for
   persistence, etc.); only reach for a toy/dev-only substitute under the
   documented, narrow conditions in AGENTS.md § 5.
3. Build important modules with clean boundaries so they can grow without a
   rewrite, but don't add microservices, distributed-systems complexity, or
   speculative abstractions the task doesn't need.
4. Don't leave disposable-prototype architecture behind (JSON-as-database,
   fake repositories, hardcoded data, direct DB calls in route handlers) —
   see AGENTS.md § 4. If temporary code is genuinely necessary, mark it as
   temporary.
5. For foundational/architectural changes, also run the
   `architecture-review` skill; for schema/query changes, run
   `database-review`.

## Git workflow

1. Run `git status` before editing anything, to see what's already there.
2. Make scoped, targeted edits — avoid unrelated formatting or mass
   rewrites.
3. Preserve any unrelated uncommitted work found from another agent or the
   user.

## Commit policy

- Split work into small, focused, logically coherent commits (see AGENTS.md
  § Commit rules for message conventions and examples).
- Tests for a change ship with that change; unrelated refactors do not.
- Never use vague commit messages.

## Push policy

- Push after each completed user-requested task, per AGENTS.md § Push rules.
- Do not let multiple finished tasks pile up unpushed.
- If push is skipped or fails, state the exact reason (no remote, auth
  failure, explicit user instruction, permissions, or exploratory task).
- Never force-push, rewrite history, or delete remote branches without
  explicit user request.

## How skills should be used

Skills in `.agents/skills/` are short, specialized checklists for a
particular kind of review or task (architecture, security, frontend, design,
backend, database, performance, testing, pre-ship). They assume the reader
already knows AGENTS.md and do not repeat it — they only add the
specialized checks for that domain. Load the skill matching the task type;
for larger tasks, multiple skills may apply (e.g. a new API endpoint touching
auth: `backend-review` + `security-review` + `testing` + `pre-ship`).

## Pre-ship

Before finishing any non-trivial task, run the `pre-ship` skill: it lists
the final checks (format, lint, typecheck, tests, build, security review,
dependency audit) to run or explicitly report as unavailable.
