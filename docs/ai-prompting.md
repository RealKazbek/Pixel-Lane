# AI Prompt Writing Standard — Pixel Lane

This document defines how humans should write prompts for Claude Code,
Codex, ChatGPT, Gemini, or any other AI coding agent working on Pixel Lane.
It is a **downstream tool for prompt authors**, not a policy file — the
canonical rules always live in `AGENTS.md` (see `docs/ai-development.md`
for the full instruction hierarchy and `docs/ai-agent-audit.md` for a
verified account of what each agent actually discovers). Nothing here
overrides, restates in full, or competes with `AGENTS.md`. Where this
document quotes a rule, it is a summary for prompt-writing convenience —
`AGENTS.md` is authoritative if the two ever appear to differ.

## Purpose

Untargeted prompts ("add a feature", "make it multilingual", "clean up the
map") force the agent to guess scope, invent architecture, or silently
skip project rules (PostgreSQL-only, kk/ru/en, Light/Dark theming, no fake
backend behavior, etc.). This standard exists so that any human, writing a prompt for any
agent, produces instructions that are complete enough to get a
project-consistent result without re-typing the whole policy every time.

## Canonical instruction hierarchy (summary)

```
AGENTS.md                 canonical, cross-agent policy — the single source of truth
    ├─ CLAUDE.md           Claude Code entry point (+ Claude-only commit-attribution rule)
    ├─ GEMINI.md           Gemini entry point (bootstrap + i18n reinforcement)
    ├─ Codex                reads AGENTS.md natively — no dedicated file
    └─ .agents/skills/*     task-specific checklists, assume AGENTS.md is already known
```

`frontend/AGENTS.md` is auto-generated by Next.js on every dev-server
start — it is framework convention noise, never project policy. Do not
cite it in a prompt as a rules source. See `docs/ai-development.md` for
the full diagram and `docs/ai-agent-audit.md` for verified vs. assumed
agent behavior. CI (`.github/workflows/ci.yml`) now runs lint/typecheck/
test/build/i18n mechanically, but it is not a required status check yet
(see `docs/testing.md`), and most of this file's judgment-based rules
(no fabricated data, no scope creep, architecture boundaries, etc.) have
no automated check at all — several rules remain documented-only.

## Required audit behavior (every prompt must trigger this)

Every Pixel Lane prompt — regardless of agent — must require the agent to,
before writing code:

1. Read `AGENTS.md` (and its own entry point: `CLAUDE.md`/`GEMINI.md`/none
   for Codex).
2. Read the relevant `.agents/skills/` checklist(s) for the task type.
3. If the task has a Notion Task ID, resolve it: retrieve the actual task
   via Notion MCP if the agent has a working connection (any agent —
   Claude Code, Codex, Gemini CLI, or another compatible agent — see
   [docs/development/notion-mcp.md](development/notion-mcp.md)), otherwise
   from the fields the human pasted (Form B below). **If neither is
   available, stop and ask for the task content instead of guessing** —
   never infer a goal, scope, or acceptance criteria from the Task ID or
   title alone.
4. Audit the *actual current implementation* of the area being touched —
   never assume a feature is missing/present because a UI button exists or
   a doc implies it. This repo has repeatedly turned out to be
   further along than a task description assumed; the correct response is
   to verify, narrow scope to real gaps, and say so — not to rebuild
   working code.
5. Report anything the instructions (or the Notion task) assume that turns
   out to be false, rather than silently working around it.

The full, numbered startup protocol this maps to lives in
[docs/ai-development.md](ai-development.md)'s "Startup protocol" section —
this list is the prompt-writer's summary of it.

## Mandatory base rules a prompt must never contradict

Derived from `AGENTS.md` — never write a prompt that asks an agent to
violate these, even implicitly:

- `AGENTS.md` is canonical; agent-specific files are entry points, not
  competing policy.
- Audit before implementing; preserve existing working functionality
  unless a change is clearly justified — no blind rewrites.
- Never invent backend readiness, APIs, or implementation status; never
  claim something works without having actually run/verified it.
- PostgreSQL is the mandatory primary database; SQLite must never become
  primary persistence; schema changes go through real Alembic migrations.
- No core production data as hardcoded JSON or frontend-only state.
- Security-by-default: no hardcoded/committed secrets, `.env` is
  persistent local config (never delete/reset it), validate at system
  boundaries.
- Strict TypeScript; preserve architectural boundaries (Traffic Engine
  independent of FastAPI/SQLAlchemy/React; domain logic independent of
  delivery frameworks — see `AGENTS.md` § 1).
- No god components/services, no giant "utils" dumping grounds, no
  duplicated logic; ~300–500 lines is a file-size signal to reconsider
  structure, not a hard rule.
- No premature microservices/Kafka/Kubernetes/Redis; scale via clean
  boundaries, not speculative infrastructure.
- Every user-facing change must ship complete `kk`/`ru`/`en` translations
  in the same change (`AGENTS.md` § 20) and pass `npm run check:i18n`
  (`frontend/`) — a missing locale is treated like a failing test.
- Every user-facing frontend change must work correctly in Light, Dark,
  and System appearance modes using the existing semantic tokens/theme
  system (`AGENTS.md` § 21, `docs/theming.md`) — a change that's only
  checked in one theme is treated like a failing test, the same as a
  missing locale.
- No unnecessary dependencies (library-first evaluation, `AGENTS.md` § 18).
- Update documentation when architecture, data flow, or workflow changes
  (`docs/architecture.md` must stay current, not aspirational).
- Planned/unimplemented features must be labeled as planned, never
  presented as live (this repo's own preview pages — e.g. Traffic,
  Simulation — already follow this pattern; point to it as precedent).

## Task execution lifecycle

Adapt to task size; every phase still applies even for small tasks.

1. **Understand** — read `AGENTS.md`, the agent's entry point, relevant
   skills, `git status`, and the actual current code/data for the area in
   scope.
2. **Plan** — identify affected modules, whether a migration/API/schema
   change is needed, risks, and consumers of anything public you're about
   to change (`AGENTS.md` § 19's "find consumers before changing a public
   contract").
3. **Implement** — focused changes only; preserve boundaries; no
   drive-by refactors of unrelated code.
4. **Validate** — run what's relevant and actually exists:
   - Frontend (`frontend/`): `npm run format`, `lint`, `typecheck`, `test`,
     `check:i18n`, `build`.
   - Backend (`backend/`): `ruff` lint/format, `mypy`, `pytest` (via
     `make backend-lint` / `backend-typecheck` / `backend-test`, or
     `make migrate` / `make migration msg=...` for schema changes).
   - Simulation: `make simulation-lint` / `simulation-typecheck` /
     `simulation-test`.
   - Cross-cutting: `node scripts/check-agents.mjs` (`make check-agents`)
     if agent-instruction files were touched.
   - CI (`.github/workflows/ci.yml`, see `docs/testing.md`) runs these same
     checks on every PR, but is **not yet a required status check** — it
     does not replace running them yourself. Never claim a check passed
     without actually running it, and say plainly if a check can't be run
     in the current environment.
5. **Review** — `git status` and `git diff`; confirm no secrets, no
   generated/junk files, no unrelated edits, nothing that overwrites
   another agent's or developer's in-progress work.
6. **Git** — small logical Conventional Commits (see `AGENTS.md` § 13),
   push to the current remote branch unless push is genuinely blocked
   (no remote, auth failure, explicit user instruction, permissions, or an
   explicitly exploratory task) — then verify `git rev-parse HEAD` matches
   `origin/<branch>` (`AGENTS.md` § 17's mandatory completion gate).
7. **Report** — see "Final report standard" below.

## Working from a Notion task: two standard forms

The task source is always Notion — but **access method depends on the
agent environment**, and Notion MCP is not assumed or required. This
applies identically to Claude Code, Codex, Gemini CLI, or another
compatible coding agent; none of them is the "default" or mandatory one —
see [docs/ai-development.md](ai-development.md)'s agent capability matrix.

### Form A — Notion MCP available (preferred)

When the agent has a working Notion MCP connection (see
[docs/development/notion-mcp.md](development/notion-mcp.md)), don't
manually copy the whole task into the prompt — let the agent retrieve it:

```
Work on PL-042 from the Pixel Lane Development Workspace.

Read the Notion task through your connected Notion MCP.
Follow AGENTS.md and relevant skills.
Audit the current implementation before editing.
Do not expand scope.
Implement, validate, and prepare the branch/PR.
```

### Form B — Notion MCP not available (fallback)

If MCP isn't configured, isn't supported by the agent/version, or isn't
authenticated in this session, the human supplies the required fields
directly — copy them from the task using
[task-template.md](development/task-template.md)'s field list:

```
Work on PL-042.

Notion MCP is not available in this session.

Task details:
- Goal:
- Module:
- Scope:
- Out of scope:
- Acceptance criteria:
- Dependencies:

Follow AGENTS.md and relevant skills.
Audit the current implementation before editing.
Do not expand scope.
Implement, validate, and prepare the branch/PR.
```

### The agent must never invent what it can't resolve

If the prompt says "work on PL-042" but the agent has neither MCP access
nor the pasted fields above, it must say so and ask for the task content
or the specific missing fields — never guess the goal, scope, acceptance
criteria, dependencies, or module from the Task ID or a task title alone.
See [docs/ai-development.md](ai-development.md)'s startup protocol, step 5.

With either form, the agent is still required to run the full startup
protocol (`docs/ai-development.md`) — reading `AGENTS.md`, resolving the
real task, auditing the implementation, reporting mismatches; these short
prompts rely on that being standing policy, not on repeating it every
time.

**Notion write access is separate from task access.** Even with Form A, an
agent may have read-only Notion MCP access. If it cannot write the task's
`Status`/`Assignee`/`Pull Request` fields itself, the human updates them
manually in Notion — see
[docs/development/notion-mcp.md](development/notion-mcp.md#no-mcp-fallback).

### Short-form template (most tasks)

Use this when the task is already well-scoped (in Notion or pasted from
the task template) and doesn't need the extended template's architecture/
security/database sections. Every field maps directly to a Tasks-database
column.

```markdown
Task ID: PL-XXX

Goal:
[One or two sentences — what outcome defines success.]

Context:
[What you already know is true right now — point at files, don't paste them.]

Expected behavior:
[What the system should do after this change.]

Scope:
[The module(s)/area(s) this touches.]

Out of scope:
[What must not change as a side effect.]

Acceptance criteria:
[Concrete, checkable conditions.]

Relevant module:
[City Model | Map / Renderer / Editor | Road Geometry | Simulation |
Traffic Control | Data Platform | Backend / API |
Frontend / Operations UI | Platform / CI | Emergency | Documentation]

Known files/areas:
[Where to start looking, if known — optional.]

Validation:
[Which checks apply — frontend/backend/simulation, per docs/development.md.]

Delivery:
Branch, PR, Notion task status update, per docs/development/project-management.md.
```

#### Example — frontend/UI task

```markdown
Task ID: PL-042

Goal:
Fix disconnected junction rendering in Demo City.

Context:
The map/editor (frontend/src/features/city-viewer/map/) renders roads by
lane count; Demo City has known junctions where two roads visually don't
meet cleanly.

Expected behavior:
Road surfaces must join cleanly at intersections without sharp caps/spikes
at normal zoom levels.

Scope:
Map/Renderer only (frontend/src/features/city-viewer/map/).

Out of scope:
Do not redesign City Model road/intersection topology or touch simulation.

Acceptance criteria:
- Demo City's known problem junctions render without visible gaps/spikes.
- No regression in road width/casing styling at other junctions.
- Verified in both Light and Dark.

Relevant module:
Map / Renderer / Editor

Validation:
make frontend-lint frontend-typecheck frontend-test frontend-build; manual
visual check of Demo City in both themes.

Delivery:
Branch fix/PL-042-junction-rendering, PR against main, Notion task moved
through Review → Done per project-management.md.
```

#### Example — backend/domain task

```markdown
Task ID: PL-051

Goal:
Add a `speed_limit_kmh` default fallback when OSM import omits it.

Context:
backend/app/city/importers/osm/defaults.py already documents fallback
behavior for missing lane/one-way tags; speed limit currently has none.

Expected behavior:
An imported road with no OSM speed tag gets a documented default instead
of a null that later breaks Traffic Engine free-flow-time calculations.

Scope:
backend/app/city/importers/osm/ only.

Out of scope:
Do not change the Traffic Engine's own handling of a null speed limit —
that fallback already exists there for manually-created cities.

Acceptance criteria:
- Missing OSM speed tag resolves to the documented default, not null.
- Existing importer tests still pass; a new test covers the missing-tag case.

Relevant module:
Data Platform

Validation:
make backend-lint backend-typecheck backend-test.

Delivery:
Branch fix/PL-051-osm-speed-default, PR against main, Notion task updated.
```

#### Example — architecture/research task

```markdown
Task ID: PL-060

Goal:
Determine whether bbox-scoped loading is actually needed yet for the
current Almaty import size, before proposing any implementation.

Context:
docs/architecture.md documents PostGIS/bbox loading as deferred until a
concrete spatial-query need exists.

Expected behavior:
A short written finding: is the trigger condition met today, and if not,
what would meet it.

Scope:
Research only — inspect current dataset size, existing query patterns,
and the documented trigger condition. Do not implement anything.

Out of scope:
No code changes, no migrations, no Notion edits beyond reporting the
finding back in this task's Notes field (this is a read-only research
task — see AGENTS.md §15 on subagent write permission).

Acceptance criteria:
A finding with evidence (actual road/intersection counts, actual query
patterns observed) and an explicit recommendation.

Relevant module:
Documentation

Validation:
N/A — no code changed.

Delivery:
Report only; no branch/PR unless the finding leads to a separate,
explicitly-scoped follow-up task.
```

## The canonical prompt template (extended)

Use the shorter Notion-task template above for most tasks. Reach for this
longer version when a task needs explicit architecture, security, database,
or performance sections spelled out — e.g. a new module boundary, a schema
change, or anything security-sensitive.

Not every section is needed for every task — use judgment, but always keep
1–3, 13, 15, and 16.

| # | Section | Mandatory? |
|---|---|---|
| 1 | Task / Goal | Always |
| 2 | Repository Instructions (pointer to AGENTS.md + entry point — don't paste it) | Always |
| 3 | Required Audit Before Implementation | Always |
| 4 | Current Context (what you, the human, already know is true right now) | Usually |
| 5 | Functional Requirements | Task-dependent |
| 6 | Architecture Requirements | When touching boundaries/schema/new modules |
| 7 | Frontend Requirements | Frontend-touching tasks |
| 8 | Backend Requirements | Backend-touching tasks |
| 9 | Database Requirements | Schema/query-touching tasks |
| 10 | Security Requirements | When handling input, auth, secrets, external data |
| 11 | Internationalization Requirements | Any user-facing UI change |
| 11b | Light/Dark Theme Requirements | Any user-facing UI change |
| 12 | Performance and Scalability | Hot paths, large data, rendering loops |
| 13 | Testing / Validation | Always |
| 14 | Documentation | When architecture/workflow/data-flow changes |
| 15 | Git Workflow | Always |
| 16 | Final Report | Always |
| 17 | Restrictions / Non-Goals | Always |

### Reusable template

```markdown
# Task
[One or two sentences: what needs to be done.]

# Goal
[The concrete outcome that defines success.]

# Repository Instructions
Read AGENTS.md as the canonical policy, plus your entry point
(CLAUDE.md / GEMINI.md / native AGENTS.md discovery for Codex) and any
relevant .agents/skills/ checklist for this task type.

# Required Audit
Before writing any code:
- Inspect the actual current implementation of [area] — do not assume it
  is missing, broken, or complete based on this prompt alone.
- Report anything below that turns out to be inaccurate instead of
  silently working around it.

# Current Context
[What you know right now: existing files/modules involved, what already
works, what's known to be missing. Keep this short — point at files
instead of pasting their contents.]

# Requirements
[Task-specific functional requirements. Be concrete: fields, routes,
behaviors, acceptance criteria.]

# Architecture Constraints
[Only the constraints relevant to this task — e.g. "this must go through
the existing city_service layer, not a new direct DB call" — not the
entire AGENTS.md.]

# Non-Goals
[Explicitly out of scope: what must NOT change, be redesigned, or be
"cleaned up" as a side effect.]

# Validation
Run the checks relevant to what changed (frontend: format/lint/typecheck/
test/check:i18n/build; backend: lint/typecheck/test/migration check).
Report exactly what ran and its result; say explicitly if something
couldn't be run.

# Git
Follow AGENTS.md's git/commit/push rules: logical Conventional Commits,
push to the current remote branch, verify remote HEAD matches local HEAD.

# Final Report
Return: audit findings, what changed and why, files touched, validation
results (pass/fail per check), known limitations, commit hash(es), push
status.
```

## Prompt quality rules

A good Pixel Lane prompt:

- States a precise goal and explicit scope boundary.
- States what you already know to be true about the current system —
  and flags what you're *not* sure about, so the agent knows to verify it
  rather than trust it blindly.
- Gives acceptance criteria, not just a vibe.
- Lists explicit non-goals when scope creep is a real risk.
- Names the validation it expects to see run.
- Names the final report shape it expects back.

A prompt must never:

- Tell the agent to "rewrite everything" or "redesign" without a specific
  reason — this repo's own instructions explicitly forbid blind rewrites.
- Assume functionality exists (or doesn't) without asking the agent to
  verify it first.
- Contain contradictory architecture instructions (e.g. asking for a
  quick SQLite prototype "for now" in a project where SQLite must never be
  primary persistence).
- Duplicate the entire `AGENTS.md` policy inline — reference it.
- Encourage shortcuts around tests, i18n, or security ("just add the
  English button for now, we'll translate later" is exactly the drift
  `AGENTS.md` § 20 exists to prevent).
- Ask the agent to declare success without having actually run validation.

## Context handling — what goes where

**A) Reference from repo files instead of copying:**
Full `AGENTS.md` policy text, the complete i18n workflow (`docs/i18n.md`),
the complete architecture map (`docs/architecture.md`), skill checklists
(`.agents/skills/`), the full instruction hierarchy (`docs/ai-development.md`).
A prompt should say "follow AGENTS.md's git rules," never paste them.

**B) Include directly because it's task-specific:**
The concrete goal, task-specific acceptance criteria, which exact
files/routes/entities are in scope, any current-context facts specific to
this task ("the Traffic page is currently a labeled placeholder — this
task activates its congestion card using data already returned by
`/api/v1/cities/{id}/traffic-analysis`").

**C) Never assume — require the agent to verify:**
Whether a feature is implemented vs. planned, whether a migration is
already applied, whether a dependency/table/endpoint exists, whether a
docs file is still accurate, whether Docker/DB is reachable in the current
environment. State these as open questions for the agent to resolve, not
as facts.

## Agent-specific notes

The architecture and policy rules are identical for every agent — only
workflow mechanics differ.

- **Claude Code** — reads `CLAUDE.md` (root and `frontend/`) automatically,
  which points to `AGENTS.md`. Respects the repo's explicit rule against
  `Co-Authored-By`/`Claude-Session` commit trailers — do not ask it to add
  attribution the repo forbids.
- **Codex** — has no dedicated instruction file; discovers `AGENTS.md`
  natively per its own convention. A prompt for Codex can skip step 2's
  "entry point" mention (there isn't one) and just say "read AGENTS.md."
- **ChatGPT** (used outside the repo, e.g. to draft a prompt or reason
  about the project) — has no repository access or automatic discovery at
  all. Any Pixel Lane fact it needs must be pasted into the conversation or
  the prompt being drafted; it cannot verify anything against the live
  repo, so prompts drafted *by* ChatGPT for use *in* the repo must still
  carry the full "Required Audit" section, since ChatGPT cannot have done
  that audit itself.
- **Gemini** — reads `GEMINI.md` first (repo convention mirroring
  `CLAUDE.md`), which points to `AGENTS.md`.

Verified vs. assumed discovery behavior for each tool is documented in
`docs/ai-agent-audit.md` — that audit found no actual contradiction in
policy content, but flagged that Codex/Gemini discovery could not be
directly executed/observed in that audit's environment. Treat "the agent
will definitely read X" as LIKELY, not guaranteed, and have the agent state
in its own report which instruction files it actually read.

## Final report standard

Every Pixel Lane task's final report should include, at minimum:

1. Audit findings (what was actually true vs. assumed).
2. What changed and why, mapped to the stated requirements.
3. Files added/changed.
4. Validation performed, with pass/fail per check — and explicit notes on
   anything that could not be run in the environment.
5. Known limitations / what was intentionally left out of scope.
6. Commit hash(es).
7. Push status, including remote-HEAD verification (or the specific reason
   push was skipped).

Normal development tasks (feature, bugfix, refactor, documentation, UI,
backend, database, infrastructure) end with this Final Report only. Do not
append a standalone "durable rules" / memory-export block (e.g. a
"PIXEL LANE ... FOR CHATGPT MEMORY" section) by default — that output is
for a distinct, narrow request: the user explicitly asking to create,
update, or export durable project rules for external memory. If a task
happens to change a durable policy (e.g. a new AGENTS.md rule), report that
change as item 2 above like any other change; do not also emit a separate
memory block unless asked.

## Anti-patterns (do not write prompts like this)

- "Make the whole app better." — no scope, no acceptance criteria.
- "Add a login page with working auth." — invents backend readiness this
  project doesn't have; should instead say "build a UI-ready login page;
  do not fake authentication since no auth backend exists."
- "Just get it working, we'll clean it up later." — invites disposable
  architecture `AGENTS.md` § 4 explicitly forbids.
- "Skip translations for now, English is fine temporarily." — directly
  contradicts `AGENTS.md` § 20's Definition of Done.
- "Use SQLite locally to make setup easier." — contradicts the mandatory
  PostgreSQL rule.
- A 3,000-word prompt that pastes all of `AGENTS.md`, `docs/architecture.md`,
  and three skills verbatim "just in case" — wastes context the agent needs
  for the actual audit and implementation; reference instead of pasting.

## Example prompts

These are illustrations of prompt *construction*, not real assigned tasks.
Do not implement them.

### Example 1 — Frontend feature (hypothetical)

```markdown
# Task
Add a "Recently viewed cities" list to the internal dashboard sidebar.

# Goal
Users who work with multiple cities can jump back to one they viewed
recently without reopening the city picker.

# Repository Instructions
Read AGENTS.md, CLAUDE.md, and the frontend-review skill.

# Required Audit
Verify how city selection currently works in `frontend/src/features/
city-viewer/` before assuming there's a "current city" concept to persist.
Confirm whether any existing local/persisted UI state mechanism exists to
extend, rather than introducing a new one.

# Current Context
The app shell sidebar and city-viewer feature already exist; city-viewer's
public boundary is its entry component only — do not reach into its
internals from the app shell.

# Requirements
- Show up to 5 most-recently-viewed cities in the sidebar.
- Clicking one navigates to that city in the existing city-viewer.
- Persist across a page reload for the current browser.

# Architecture Constraints
Must not add new backend endpoints — this is client-side UI state only.
Must not duplicate city-viewer's domain types; reuse its existing City id.

# Non-Goals
Do not change city-viewer's internal selection/editor logic. Do not add a
global state management library.

# Internationalization Requirements
All new labels need kk/ru/en entries in the appropriate messages namespace.

# Light/Dark Theme Requirements
Use existing semantic tokens (AGENTS.md § 21) — no hardcoded single-theme
colors. Verify readable in both Light and Dark before calling this done.

# Validation
npm run format / lint / typecheck / test / check:i18n / build (frontend/).

# Git
Follow AGENTS.md's commit/push rules; verify remote HEAD after push.

# Final Report
Audit findings, files changed, validation results, limitations, commit
hash(es), push status.
```

### Example 2 — Backend/database feature (hypothetical)

```markdown
# Task
Add a `Camera` entity to the City Model for future computer-vision
integration (persistence only — no CV logic).

# Goal
The domain model can represent a camera's location and the road/
intersection it's associated with, ready for a future importer/consumer.

# Repository Instructions
Read AGENTS.md and the architecture-review + database-review skills.

# Required Audit
Inspect `backend/app/city/` to confirm the exact layering convention used
by an existing similar entity (e.g. how `ParkingZone` or `TrafficLight` is
structured across domain/schemas/models/validators/repositories/services/
api) before adding a new one — match that pattern, don't invent a new one.

# Current Context
City Model v1 already has Road/Lane/Intersection/TrafficLight/TrafficRule/
ParkingZone/TrafficDemand, normalized in PostgreSQL with real FKs/cascades.
No PostGIS yet; geometry uses generic Point/Polyline value objects.

# Requirements
- New `Camera` entity: id, city_id, position (Point), optional road_id or
  intersection_id association, status enum (active/planned).
- A real Alembic migration.
- Wired into city_mapper/city_builder and the city read/create API the
  same way existing entities are.

# Database Requirements
PostgreSQL only; real FK constraints with ON DELETE CASCADE from city_id;
no JSON blob shortcut unless justified the way Road.geometry's JSONB
exception is documented.

# Non-Goals
Do not implement any camera feed/CV logic. Do not add this to the frontend
in this task unless explicitly asked.

# Validation
make backend-lint / backend-typecheck / backend-test; make migrate against
a real Postgres; confirm migration applies cleanly from a clean database.

# Final Report
Audit findings, schema/migration diff, files changed, validation results
(explicitly note if Postgres wasn't reachable in the environment), commit
hash(es), push status.
```

### Example 3 — Cross-stack architectural feature (hypothetical)

```markdown
# Task
Introduce bounding-box (viewport-based) loading for City Model road data,
replacing "always fetch the whole city" for cities beyond demo scale.

# Goal
Large cities can be viewed without loading their entire road network into
the frontend at once, without a rewrite of the City Model domain layer.

# Repository Instructions
Read AGENTS.md fully (architecture, database, performance sections), plus
architecture-review, database-review, and performance-review skills.

# Required Audit
Confirm current behavior: does the city API already return the whole city
per request? Is PostGIS installed? What's the actual size of the Almaty
demo dataset today — is this genuinely needed yet, or premature? Report
findings before proposing an implementation.

# Current Context
docs/architecture.md documents PostGIS as deferred until a concrete
spatial-query need exists; docs/city-model.md documents the same trigger
condition. This task should only proceed with a real justification found
```
